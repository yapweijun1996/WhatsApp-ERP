# Least-privilege staff chat access

`CHAT_ONLY` is an explicit host-configured role. It permits `CHAT_SEND`, `CHAT_TAKEOVER` and `CHAT_RESUME` only for one account and a finite list of canonical conversation IDs. It never permits `POST`, `CONFIRM`, `DO` or `RESET`. Each operation checks its own permission, scope and live capability before any effect. Existing `STAFF_BOOTSTRAP_CREDENTIAL` remains the broad `LEGACY_STAFF` compatibility path; no chat credential silently falls back to that role.

Capabilities are opaque process-local objects with copied, immutable grants. Request-body labels, Access identity, copied objects, a missing scope, wildcard, cross-account/conversation, exact expiry boundary and revoked capability fail closed. Sessions expire after at most one hour and no later than the configured absolute grant expiry. Logout and replacement login revoke the old capability; process exit loses all sessions. A fresh login cannot renew an expired configured grant. Restart without the configuration disables that bootstrap. No persistent authorization table or schema migration is added.

The existing ownership/revision, direct-recipient proof, audit, durable intent, idempotency and single-provider-owner boundaries remain. The writer transaction rechecks authorization after the asynchronous connection wait, and the manual wire fence checks the same capability immediately before provider dispatch. Logout/expiry before reservation has no audit, intent or provider effects. Revocation after reservation blocks any later dispatch and conservatively retains UNKNOWN if the provider outcome cannot be established. An already-dispatched provider request may finish. Never retry it automatically or infer physical delivery from submission.

Permission loss does not silently release a HUMAN takeover or replay held inbound. The same approved staff subject can sign in again while its grant is valid and resume once prior delivery/processing drains. An expired grant or inaccessible owner requires separately reviewed recovery; no automatic owner reassignment or commercial action is added.

Chat HTTP actions retain the HttpOnly/SameSite=Strict cookie (Secure in production), JSON and custom same-origin action header. Cross-site and same-site browser requests are rejected; CORS is not enabled. The backend derives the account and canonical conversation from its current transport and database rather than accepting a body account. Every idempotent replay is reauthorized. Commercial services now require POST/CONFIRM/DO permissions even when invoked below HTTP. Chat sessions cannot use the synthetic reset route.

The session projection shows role, explicit permission names, approved scope and expiry, with no credential. The inbox uses scoped chat permissions and disables commercial buttons/evidence unless permitted. Authenticated chat-only access is labeled “no commercial permissions”; missing permission data does not enable a commercial action. Logout is available in Settings. Unsent text remains in page memory and is never sent by polling.

## Private owner handoff after source/CI/independent review

1. Review the exact PR head and deployment/restart plan. This source PR authorizes neither deployment nor credential/grant activation. Preserve the current Air working DB, paired session and account inquiry configuration.
2. Through the existing protected owner-local environment/secret manager, supply an owner-controlled credential as `STAFF_CHAT_BOOTSTRAP_CREDENTIAL`. Do not paste a credential into chat, commit it, print it, or reuse the broad staff credential. No credential is generated by this feature. If no owner-controlled chat credential exists, its provisioning needs a separate security action review.
3. Supply non-secret `STAFF_CHAT_ACCESS_JSON` with only `subject`, `accountId`, `conversationIds` and `expiresAt`. Use a stable attributable staff subject, the actual paired account, exact canonical IDs from the read-only conversation API, and an explicit UTC ISO expiry. Example structure (placeholders, not activation):

   ```json
   {"subject":"OWNER_APPROVED_SUBJECT","accountId":"ACTUAL_ACCOUNT_ID","conversationIds":["ACTUAL_CANONICAL_CONVERSATION_ID"],"expiresAt":"OWNER_SELECTED_ISO_EXPIRY"}
   ```

   Missing/malformed/extra fields, empty/wildcard/duplicate IDs, invalid expiry, or an identical broad/chat credential stop startup with a generic configuration error. Arrays are copied at startup; changing a running process's environment cannot widen it.
4. Only after the appropriate deployment and persistent-access action reviews, apply the private configuration using the established owner workflow. Staff sign-in sends that existing credential once in the backend Authorization header; the page clears it immediately, uses no browser storage, and displays the resulting role/scope/expiry. Cloudflare Access alone remains insufficient.
5. Verify the read-only permission projection before any explicit takeover or manually chosen reply. Team QA uses synthetic tests; no live message is required by this handoff. To revoke immediately, sign out (current capability); to disable future logins, remove the private chat configuration and use the reviewed restart procedure. Review retained HUMAN ownership/UNKNOWN attempts before recovery.

This branch reads no private runtime credential/session/database, writes no live grants, sends no real message, and changes no deployed business processing.
